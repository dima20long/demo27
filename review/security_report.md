# Отчёт по безопасности

## SEC-01 — Несанкционированное назначение роли администратора при регистрации (Critical)
- Файл: `app/blueprints/auth.py`, `register()`, строки 123–130.
- Endpoint `/api/auth/register` не требует авторизации и берёт `role` напрямую из JSON: `data.get("role", "Пользователь")`, после чего создаёт пользователя с этой ролью.
- Пользователь может отправить `role="Администратор"` и зарегистрировать аккаунт с административными полномочиями. Это подтверждается кодом, не только предположением.
- Рекомендация: не принимать роль из публичного запроса; всегда назначать роль «Пользователь». Назначение администратора — только из защищённого admin endpoint. Добавить тест, пытающийся зарегистрировать администратора.

## SEC-02 — CRUD API бизнес-данных без аутентификации (High)
- Файл: `app/views/base_view.py`, строка 42 — `decorators = []`; views наследуют этот класс.
- `app/__init__.py` регистрирует endpoints из `app/views/`.
- Views clients/products/materials/operations/specifications/sales-orders/production-orders не содержат `login_required`/role checks.
- Рекомендация: защищать API сессией/токеном и серверной проверкой прав; покрыть все методы GET/POST/PUT/DELETE тестами.

## SEC-03 — CAPTCHA отключена (Medium/High)
- Файл: `app/blueprints/web.py`, login route.
- Переменная `captcha_ok` выставлена `True`; проверка не производится. Сама капча реализована отдельным модулем, но login flow не использует её результат.
- Рекомендация: связать серверную проверку CAPTCHA с входом или отключить заявленную защиту в интерфейсе. Не использовать CAPTCHA как замену ограничению попыток.

## SEC-04 — Секретный ключ и пароль БД имеют небезопасные fallback значения (High)
- Файл: `app/config.py`, строки 53 и 59.
- `SECRET_KEY` fallback: `production-is-system-secret-key-change-me`.
- `DATABASE_PASSWORD` fallback: `12345`; тестовая БД fallback URI также содержит этот пароль.
- Если переменные окружения не заданы, приложение использует предсказуемые значения.
- Рекомендация: отказ от запуска в production при отсутствии секретов; хранить секреты вне репозитория; исключить слабый fallback для production и тестов.

## SEC-05 — Debug mode и bind на все интерфейсы (High для deployment)
- Файл: `run.py`, строка 9, запуск `app.run(host='0.0.0.0', port=5000, debug=True)`.
- Debug включён и приложение слушает все сетевые интерфейсы. Это опасно при запуске не только на локальной машине/в изолированной учебной среде.
- Рекомендация: debug включать только локально; production запускать через WSGI сервер; не публиковать debug endpoint.

## SEC-06 — Возможный XSS через `innerHTML` (High, подтверждённые точки внедрения)
- `web/notes.html`, строки 21–30: `note.title_user` и `note.content` вставляются в HTML строку через `innerHTML`; эти поля формируются пользовательскими заметками. Это создаёт DOM-XSS риск.
- `web/clients.html`, строки 24–29: поля `client.name`, `client.inn`, `client.client_type`, `client.phone` вставляются в HTML через `innerHTML`; поля поступают из API/форм и должны считаться недоверенными.
- Аналогичный шаблон используется в таблицах/карточках других страниц. Для подтверждения конкретной эксплуатируемости нужен тест payload в браузере; статический анализ подтверждает опасный sink и пользовательские источники, но не тестировал выполнение payload.
- Рекомендация: вместо интерполяции пользовательских значений в HTML использовать DOM APIs и `textContent`; избегать inline event handlers; при необходимости использовать безопасную HTML sanitizer.

## SEC-07 — Валидация роль в API регистрации отсутствует
- В отличие от admin views, публичный register не проверяет значение role на допустимость; ограничения модели могут ограничить значения, но не предотвращают назначение «Администратор».
- Рекомендация: игнорировать поле role в публичной регистрации и валидировать все enum поля сервером.

## SEC-08 — CSRF и cookie-based session
- Приложение использует Flask-Login с cookie/session; в просмотренных файлах не обнаружена интеграция CSRF-токенов для изменяющих web/API запросов.
- Это требует подтверждения полной конфигурацией и deployment. Рекомендация: включить CSRF protection (Flask-WTF или аналог) для cookie-based POST/PUT/DELETE, с тестами.

## SEC-09 — CORS для изображения CAPTCHA открыт
- Файл: `app/blueprints/puzzle_captcha.py`, GET fragment route добавляет `Access-Control-Allow-Origin: *`.
- Для публичного изображения это может быть допустимо; если endpoint использует чувствительные данные/токены, ограничить CORS. Не классифицируется как самостоятельная уязвимость без дополнительного контекста.

## Приоритет исправлений
1. Убрать назначение роли из публичной регистрации.
2. Закрыть CRUD API аутентификацией и авторизацией.
3. Устранить XSS-risk в динамическом HTML.
4. Убрать небезопасные секреты по умолчанию; выключить debug для production.
5. Восстановить реальную проверку CAPTCHA/добавить CSRF защиту.
