# День 3 — Анализ бизнес-логики (Logic Review)

## Проект
Demo27 — веб-приложение на Flask

## Область проверки

В ходе анализа были проверены следующие компоненты:

- Аутентификация и регистрация пользователей
- Заказы продаж
- Производственные заказы
- Товары и ценообразование
- Клиенты
- Спецификации
- Административные функции
- Слой репозиториев

## Найденные замечания

### 1. Использование цен с будущей датой действия

**Приоритет:** Средний  
**Область:** Расчёт цен и себестоимости

При получении актуальной цены выполняется сортировка по дате действия, но не всегда учитывается, что дата действия цены может находиться в будущем.

**Риск:** В расчётах могут использоваться цены, которые ещё не должны действовать.

**Рекомендация:** При выборе цены учитывать только записи, дата действия которых не превышает текущую дату.

---

### 2. Раздельное сохранение заказа продажи и производственного заказа

**Приоритет:** Средний  
**Область:** Создание заказов

Заказ продажи и связанный с ним производственный заказ сохраняются отдельными операциями фиксации транзакции.

**Риск:** Если создание производственного заказа завершится ошибкой после сохранения заказа продажи, в базе данных может остаться заказ без связанного производственного заказа.

**Рекомендация:** Рассмотреть возможность объединения связанных операций в одну транзакцию, чтобы при ошибке изменения отменялись целиком.

---

### 3. Отсутствие ограничения скидки в 100%

**Приоритет:** Средний  
**Область:** Заказы продаж

В API не обнаружена проверка, ограничивающая размер скидки диапазоном от 0 до 100 процентов.

**Риск:** Скидка более 100% может привести к отрицательной стоимости позиции или заказа.

**Рекомендация:** Добавить проверку допустимого диапазона скидки на уровне API или бизнес-логики.

---

### 4. Возможность конфликта при генерации номеров заказов

**Приоритет:** Средний  
**Область:** Заказы продаж и производственные заказы

Номер нового заказа формируется на основе анализа существующих номеров и вычисления следующего значения.

**Риск:** При одновременном создании нескольких заказов запросы могут получить одинаковый номер.

**Рекомендация:** Использовать более надёжный механизм генерации уникальных номеров, учитывающий параллельные запросы.

---

### 5. Пропуск некорректных позиций заказа

**Приоритет:** Средний  
**Область:** Заказы продаж и производственные заказы

При обработке позиций заказа некорректные идентификаторы товаров могут пропускаться без прекращения создания заказа.

**Риск:** Заказ может быть создан не полностью, без явного уведомления пользователя об исключённых позициях.

**Рекомендация:** Проверять все позиции перед созданием заказа. Если хотя бы одна позиция некорректна, возвращать ошибку валидации.

---

### 6. Недостаточная обработка ошибок при вводе даты

**Приоритет:** Низкий  
**Область:** API заказов

В некоторых обработчиках используется преобразование даты без обработки ошибок некорректного формата.

**Риск:** При передаче неправильной даты может возникнуть необработанное исключение.

**Рекомендация:** Добавить проверку формата даты и возвращать пользователю ответ HTTP 400 при некорректных данных.

---

### 7. Повторяющиеся запросы к базе данных при получении цен

**Приоритет:** Низкий (производительность)  
**Область:** Товары, спецификации и расчёты

В некоторых местах для каждой отдельной записи выполняются дополнительные запросы для получения актуальных цен.

**Риск:** При увеличении количества товаров, материалов или операций возрастает число запросов к базе данных, что может снижать производительность.

**Рекомендация:** Рассмотреть оптимизацию запросов, получение данных пакетами или использование более эффективных способов загрузки связанных данных.

---

### 8. Недостаточная проверка входных данных

**Приоритет:** Низкий (требует дополнительной проверки)  
**Область:** Спецификации и CRUD-операции

В некоторых API-методах не обнаружена полная проверка числовых значений перед передачей их в сервисы или базу данных.

**Риск:** Некорректные значения могут приводить к ошибкам сохранения или неправильным расчётам.

**Рекомендация:** Внедрить единый подход к проверке количеств, цен, скидок, дат и статусов.

---

## Недостатки тестового покрытия

- Недостаточно тестов для API производственных заказов.
- Регистрация пользователей недостаточно покрыта тестами.
- Рекомендуется добавить тесты на некорректные входные данные, граничные значения и ошибки транзакций.

## Итог

В ходе анализа обнаружены потенциальные риски, связанные с расчётом цен, созданием заказов, проверкой входных данных и целостностью данных.

Замечания необходимо расставить по приоритетам и, где возможно, подтвердить дополнительными тестами перед исправлением.

Следующий этап — проверка безопасности приложения и используемых зависимостей, после чего выбор наиболее важных замечаний для исправления.
